# Test data

Everything in this folder is fake. It is generated by `scripts/generate-fake-data.ts` with fixed seeds, so the output is the same on every run. A unit test fails if these files differ from what the generator produces.

```sh
node scripts/generate-fake-data.ts                                   # rewrite the files here
node scripts/generate-fake-data.ts --rows 5000 --out tmp/large.csv   # a larger sample, not committed
```

## Files

- `sample/support-tickets.csv` and `sample/support-tickets.xlsx`: the same 200 support tickets, reviews and survey comments for a fictional invoicing and time-tracking app, in German and English. Columns: `id`, `created_at`, `channel`, `rating`, `plan`, `country`, `customer_name`, `customer_email`, `message`. The customer columns are there to exercise the default "Drop" role for columns with personal headers.
- `eval/generated.jsonl`: 1,200 labelled messages from the same templates. The generator rotates through the types of personal data so each type has at least 50 examples per language, and 1 in 12 items has none.
- `eval/hard-cases.jsonl`: hand-written edge cases (`scripts/fake-data/hard-cases.ts`): obfuscated emails, invalid checksums, order numbers that look like phone numbers, version strings that look like IP addresses, ordinary dates, numbers that look like postcodes.
- `eval/names.jsonl`: hand-written name cases (`scripts/fake-data/names.ts`): 286 German and English sentences with invented names typical of 13 communities living in Austria, each with a `group` and a `split` (`dev` for tuning, `test` for the published numbers), and 26 dev-only look-alikes without a group: greetings and sign-offs followed by words that are not names ("Hallo Team", "Dear Customer Support"), to measure precision. The group exists only to report recall per group; Painfold never infers anyone's origin.
- `eval/long-texts.jsonl`: 8 long German and English messages (`scripts/fake-data/long-texts.ts`), each with names near the start, in the middle and at the end, to check that names are found past the name model's 512-token window. Only reported.
- `eval/name-detections.json`: what the name model found in each evaluation set, measured in the browser (`npm run eval:names -- --set <set> --save`); the published numbers are computed from it, and an end-to-end test checks it still matches.

- `eval/analysis/items.jsonl`: 240 invented feedback messages for the Stage 3 analysis evaluation (#129), 120 in English and 120 in German, about the same kind of invoicing and accounting app, some already cleaned (`[NAME_1]`). Each has a `split`: 60 `dev` (for tuning prompts) and 60 `test` (run once) per language, chosen by a seeded shuffle. The German messages follow the same themes as the English ones in German wording, with Austrian terms (UVA, FinanzOnline, Lohnverrechnung); many are close to translations, which makes the two languages comparable but not independent. The items were written by the person writing the prompts; the labels are not.
- `eval/analysis/labelling-en.xlsx` and `labelling-de.xlsx`: the spreadsheets handed to the labellers, generated from the items (`python3 scripts/labelling/make_sheets.py`): guidelines with definitions and worked examples (in German for the German file), one row per item with dropdowns for sentiment and type, and a themes tab where each labeller keeps the names they use. The English half is labelled by Francis, the German half by a German-speaking classmate. The split is not in the files.
- `eval/analysis/labels-en.jsonl` and `labels-de.jsonl` (once labelled): written by `npm run labels:convert -- <filled file>`, one line per item: `{ id, lang, split, jobs, pains, gains, sentiment, type, comment? }`. The converter refuses files with problems and names each one: missing or invalid sentiment or type, names not on the themes tab, placeholders in names, changed texts, and missing or unknown rows.

Each evaluation line is `{ id, lang, text, spans: [{ start, end, type, text }] }`. Text not covered by a span is not personal data. Types are listed in `core/pii-types.ts`; `NAME` and `PLACE` are found by the name model (Stage 2).

## Where the values come from

- **Email addresses and URLs** use the reserved `example.com`, `example.org` and `example.net` domains (RFC 2606).
- **IP addresses** come from the documentation ranges `192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24` and `2001:db8::/32` (RFC 5737, RFC 3849).
- **German landline numbers** use the Bundesnetzagentur block for media productions, Berlin `030 23125 000` to `999` ([Bundesnetzagentur, Drama Numbers](https://bundesnetzagentur.de/DE/Fachthemen/Telekommunikation/Nummerierung/DramaNumbers/artikel.html)).
- **UK numbers** use the Ofcom numbers for drama, mobile `07700 900000` to `900999` and London `020 7946 0000` to `0999`, which Ofcom does not allocate to providers ([Ofcom, numbers for drama](https://www.ofcom.org.uk/phones-and-broadband/phone-numbers/numbers-for-drama)).
- **Austrian numbers** are random, in the mobile ranges (0)650 to (0)699. Checked in November 2026: RTR, the Austrian regulator, publishes no block of fictional or reserved numbers, and names no unassigned mobile prefix; the gaps in its list of assignable mobile prefixes ((0)654, (0)656, (0)658, (0)662) are the start of Salzburg-region landline area codes, so they are no safer ([RTR, mobile numbers](https://www.rtr.at/TKP/was_wir_tun/telekommunikation/nummerierung/nationaleRufnummern/mobileN.de.html)). The numbers are invented, not taken from anyone, but not guaranteed to be unassigned.
- **IBANs, SV-Nummern and VAT IDs** are random with valid check digits, plus the documentation IBANs `DE89 3704 0044 0532 0130 00` and `AT61 1904 3002 3457 3201` and the textbook SV-Nummer `1237 010180`.
- **Card numbers** are the published test numbers of Visa, Mastercard and American Express.
- **Surnames** are invented in the generated data. In the hand-written name cases, names are combinations of common first names and surnames from each community, made up for testing and not meant to refer to anyone. First names are common ones. Street names are generic; towns and postcodes are real places, which are not personal data on their own.

## Limits

The generated evaluation items share templates with the sample file, so detectors could be tuned to those sentences. The hand-written hard cases are separate for that reason, and accuracy is reported for both.
